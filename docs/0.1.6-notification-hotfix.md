## Correction and delivery ownership

`AutoReports.Pending` now retains its notification origin through retries. New `finalized()` work is eligible to notify; startup `recover()` work is silent, including repairs, format upgrades, incomplete exports and their subsequent retries. Recovery failures and report availability remain visible through their existing status paths. Manual checkpoint recovery still reports its meaningful recovery status and exports normally; it does not present the historical session as a newly finished fight.

A new `ExportNotifications` queue owns ordinary completion delivery. Production completion events are separate from free-form failure/status strings:

1. Recording finalization creates the same history entry and export job as before.
2. The existing single storage worker persists JSON, checks existing receipt/output hashes and runs any required export.
3. The successful receipt is written only after both report files exist and are validated.
4. Only newly finalized work that actually commits a receipt creates a completion token. Its operation identity carries the recording UUID and existing content/options/format digest. Matching receipts return before creating a token.
5. The same token has one atomic claim. Duplicate/concurrent callbacks carrying it cannot enqueue it again, including after delivery, expiry or overflow. There is no global growing set of delivered UUIDs.
6. The synchronized session queue transfers the event to the real Minecraft end-of-tick path. It consumes the entry before chat insertion, preventing reentrant or later ticks from redispatching it. Production `notice()` executes immediately on that client thread.
7. No world, dimension, server or analytics-screen event resets or repopulates the queue. Initialization is guarded across initializer instances, so callbacks/workers cannot be installed twice.

The persisted successful receipt owns export idempotency; the ephemeral one-shot token owns delivery idempotency. Tokens are created once by publication, never reconstructed from receipts. Startup recovery is always silent for ordinary success, so even a repair after restart cannot replay a delivered message. No persistent notification database or disk acknowledgment is added. A crash before queued chat delivery may lose that ordinary notice; saved history and report availability remain authoritative.

Explicit unavailable-player policy: retain up to **128** completions for **120 monotonic seconds**. Expire at the deadline; discard the oldest on overflow. These disposals are final. Fresh completions still notify independently even when their text or human-readable filenames coincide. Failure notices use the existing separate status path. A failed fresh export retains eligibility and notifies once on later successful retry; a failed recovery repair stays silent on success.

The six configured-server rules, generic/manual capture policy, recording format, export format, receipt format, checkpoint format, historical decoder and existing retry cadence are unchanged.

## Resource use and preservation

The queue performs no disk I/O and no history/receipt scans. Empty ticks check one bounded deque; publication and consumption are synchronized. A delivered/disposed token retains only its own claim if a caller still holds it; the queue drops its reference. The existing worker, 128 retry snapshots, 1,000-entry availability cache and startup scan remain unchanged. No new listener is installed during reset, reconnection or GUI navigation.

Original evidence was hashed before analysis and verified again before commit. The live owner's client was already running: four open log files initially refused PowerShell's exclusive hash read; shared read-only hashes were recorded separately. Final verification finds **1,498/1,499 original files unchanged** in size, modification time and SHA-256, including all **1,350 KWAMSTER data files**. Only the active `latest.log` grew: its entire original byte prefix retains the recorded SHA-256, establishing an external append. All **236 tracked original project files still exist**; project before/after manifests and the intended diff are retained. No clean task, original-file deletion or live-instance write was performed.
