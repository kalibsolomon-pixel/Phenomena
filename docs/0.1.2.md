## Multiplayer evidence

Read-only investigation covered the Aurora instance's KWAMSTER directory and 54 native Minecraft logs, including latest.log and rotated gzip logs. 47 contained chat; seven did not. Launcher mirror logs were inventoried and excluded from duplicate counting. Logs do not establish that titles, actionbars or every chat message were received.

The reusable script is `scripts/diagnose_multiplayer.py`. It preserves original message text, source file/line, timestamp and channel uncertainty; extracts start/result/kill announcements; groups likely matches; correlates by time and participant name; and reports ambiguous groups, unmatched announcements and unmatched recordings. It never edits inputs or changes historical results.

Run locally:

```powershell
python scripts/diagnose_multiplayer.py INSTANCE --out .local-diagnostics/multiplayer
```

The timezone defaults to explicit UTC-04:00 for these September/October 2026 logs. Supply `--timezone` when analyzing other dates/zones. IANA zones require an available timezone database. Outputs contain private evidence and are ignored by Git.

The investigation found 3,940 announcements in 1,120 likely groups. All 52 recordings had a likely correlation; 12 groups were ambiguous or fragmented. 1,059 groups had no recording, largely from historical sessions predating this recording set. Correlation is diagnostic, not proof of a result.

Observed formats, with names replaced:

- PVPHQ: `► Opponent: PlayerB`; `► Winner: PlayerA (7.9 ❤) [Click]`.
- Minemen: multiline `Casual Match`, map, opponent and ping block.
- Minemen: multiline `Match Results (Click to view)` followed by `🏆 Winner: PlayerA  ▏  ☠ Loser: PlayerB`.
- Minemen: `PlayerB was killed by PlayerA!`.
- Archived logs: `Round N started!`.

`You Won`, `PlayerA Won`, losing equivalents and bare end markers are supported as conservative generic fallbacks requested by the owner. They were not found as result formats in this evidence set. Tournament countdowns and player messages containing “starts in” were found and deliberately excluded from authoritative rules.

## Lifecycle and outcome rules

`Announcements.Rules` provides host-scoped adapters; the combat tracker has no server-specific regexes. System-chat packets are observed at the dispatch tail, separately from signed player chat, disguised chat and actionbar overlays. Ordinary relayed chat is rejected by whole-message format matching.

Named starts create active matches even before combat, covering forfeits without invented attack statistics. A recorded monotonic timeline origin preserves the wait before the first attack in both GUI and HTML. The first matching observed player UUID binds to the announced opponent. New starts separate rounds. Unrelated targets cannot silently replace a participant in an announced duel. Duplicate announcements, unrelated participants, mismatched hosts, uncertain origins and expired results cannot confirm results.

Paired winner/loser or kill messages must name the local player and the active opponent. An exact known adapter can then record a confirmed *server-declared* result. One-name messages cannot identify an opponent independently: they require a scoped round plus endpoint evidence and remain inferred. Same-opponent rematches also require endpoint evidence and remain inferred because these messages lack round IDs. The first two seconds of an announced round reject results conservatively. Generic results never become confirmed merely from keywords.

Death, world changes and bare end messages enter a configurable three-second grace period. A qualifying result finalizes the current round; a new round flushes the preceding one. Finalized records are immutable and late messages cannot rewrite unrelated history. Announced matches use a separate 60-second inactivity fallback; unknown servers retain the eight-second combat fallback. Dense motion/input/velocity traces are thinned at 9,000 events, reserving the 10,000-event limit for combat observations.

Match evidence includes original local text, rule, origin, acceptance, monotonic time, round identity, outcome confidence and timeline start. Shared copies redact all announcement text and player/server identity.

## Automatic recordings and exports

With recording enabled (default), finalization queues JSON persistence and self-contained HTML generation immediately, independently of GUI use. Filesystem work uses a single bounded worker with 128 queued tasks and at most 128 pending retry snapshots. Existing recordings are preserved; automatic saves do not prune them. Retention bounds in-memory history. The legacy manual-save budget does not delete automatic recordings.

Paths relative to the Minecraft game directory:

| Artifact | Path |
| --- | --- |
| New local recording | `kwamster/fights/Fight vs PlayerB yyyy-MM-dd HH-mm-ss/<fight-uuid>.json` |
| Unknown opponent | `kwamster/fights/Fight yyyy-MM-dd HH-mm-ss/<fight-uuid>.json` |
| Default anonymized report | `kwamster/exports/Fight yyyy-MM-dd HH-mm-ss/index.html` and `report.json` |
| Named report, explicit privacy opt-out | `kwamster/exports/Fight vs PlayerB yyyy-MM-dd HH-mm-ss/index.html` and `report.json` |
| Completion receipt | `kwamster/report-state/<fight-uuid>.json` |
| Legacy recording, still supported | `kwamster/fights/<fight-uuid>.json` |

Local folder naming always retains a known opponent, regardless of anonymization. Shared filenames and HTML/JSON remove identifiers by default. Names are sanitized to safe bounded segments; collisions append the full fight UUID and occupied unrelated directories are preserved. No existing recording is destructively migrated. Report and recording IDs match.

Writes flush the temporary file and use atomic replacement. Unsupported atomic replacement fails while preserving the original. Raw recording persistence precedes export publication. An ownership marker prevents partial exports from creating extra folders; a receipt is committed only after JSON and HTML succeed. Source/options and output digests prevent duplicate publication and detect truncated completed files. Three immediate attempts are followed by 30-second retries and startup recovery. Errors are logged and surfaced in status. Manual Export also persists an in-memory fight if a prior automatic save failed.

Queue exhaustion is reported; retained pending snapshots can retry. A hard process termination before the initial disk write, or an indefinitely unavailable/full disk, can still lose unsaved session data. There is no promise of an atomic transaction across all report files; the receipt identifies completed publication and repairs partial files on recovery. Reads remain bounded by event count, per-file size and loaded timeline budget.

## Corrected measurements

**Weapon timing:** attempted melee intervals, including eligible empty swings, use the held item/slot/attribute-component identity, effective attack speed and vanilla effective cooldown. No weapon-category cooldown table drives capture. Swords, axes, tridents, fists, ordinary items and maces are exercised. Previous-attack cooldown defines a two-cooldown window. One cooldown ±1 client tick is perfect; earlier is fast; later through two cooldowns is slow. Switches and longer gaps reset the sequence; openers are ungraded. Zero/nonfinite speed becomes unavailable and remains serializable. Client attribute modifiers are captured; invisible server mechanics remain unavailable. Projectile throws do not enter this melee path.

**Perfect reach:** independent of timing/readiness. Only a unique source-confirmed local melee correlation can count or play the special sound. Both ordinary player attacks and mace-smash damage sources are recognized. Ray contact must be unobstructed. Geometry is interpolated eye to the entry point on the client target box inflated by pick radius. Nearest-box fallback distances cannot reward the sound. Default inclusive window: 3.00 ± 0.06 blocks. Enable, target, tolerance, sound identifier, volume and pitch remain configurable. Frozen fight policy keeps counts and sound eligibility consistent. Duplicate tick observations cannot consume multiple pending attempts.

**Jump resets:** actual grounded jump actions are separate from input presses and server velocity diagnostics. Water/climb/riding cases are excluded. Held input scores once per press; prevented input does not become a jump. Signed client-tick offsets use nearest damage in tick distance, with monotonic time for tie-breaking and diagnostics. Zero is an ideal-timing candidate; ±4 ticks is an attempt candidate. Early jumps before initial damage can be retained, and event ordering is tested. No successful knockback cancellation is claimed. Historical recordings without ticks show unavailable classifications.

**Melee aim:** preserve raw normalized XYZ, eye, box, reach/contact and derived region separately. Nearest reachable surfaces change with elevation, size and pose; opponent eye level is not a universal target. The ideal region uses an inset from fragile edges and explicit heuristic distance bands. Blue/green/orange/purple regions have text legends for ideal/good/peripheral/poor alignment. Browser reports select a hit and project its actual contacted side or top/bottom face. Current-ray obstruction is checked; other surface occlusion cannot be reconstructed. Projectile placement is not graded using these rules.

The tabbed GUI retains its visual design and adds outcome evidence, report availability, weapon interval tables, reach counts, tick offsets and aim classifications. Recording schema 1 and 2 load; missing older measurements remain unavailable. Shared payload format is 3.
